CESVI RAT (Reconstrucción y Análisis de Tránsito) is a full-stack forensic platform developed for **CESVI México** — the Centro de Experimentación y Seguridad Vial. The system supports professional accident investigators in documenting, reconstructing, and analyzing road traffic incidents.

I joined the project as **database coordinator**, responsible for the full data layer and cross-team technical integration.

---

## The problem

Accident reconstruction specialists relied on fragmented tools: manual measurements recorded on paper, velocity calculations done in spreadsheets, and no unified system to store, query, or cross-reference incident data.

The challenge was to build a platform that could handle the full workflow — from initial scene documentation to final forensic report — while being robust enough for professional use in legal and insurance contexts.

---

## Project objectives

- Design a normalized relational schema covering all aspects of accident documentation
- Implement a Laravel backend with clean model relationships and migration history
- Integrate forensic calculation logic (deformation, velocity, energy transfer)
- Deliver full technical documentation to the client

---

## Technologies used

- **MySQL** for the relational database
- **Laravel** (PHP) for the backend and ORM layer
- **Eloquent** for model definitions and relationships
- **PHP Artisan** for migration management
- **Git & GitHub** for version control and team coordination

---

## Database design

The schema grew to **54 tables** covering:

- Incident metadata (date, location, weather, road conditions)
- Vehicle inventory and damage documentation
- Occupant and witness records
- Deformation measurements per impact zone
- Velocity and energy calculations per vehicle
- Reconstruction timeline and event sequence
- Report generation and case status tracking

Normalization was applied to 3NF across all core entities. Foreign key constraints and indexed lookup tables were used throughout to enforce referential integrity.

---

## Forensic calculation layer

The system implements the **McHenry CRASH3** methodology for energy-based velocity estimation. Key inputs include:

- EBS (Equivalent Barrier Speed) coefficients by vehicle category
- Crush depth measurements from the scene (6-point profiles)
- Stiffness coefficients A and B per vehicle class

These values feed into a velocity range estimate for each involved vehicle, which the system logs, stores, and flags for review.

## Team coordination

The project ran with a cross-functional structure:

| Track | Responsibility |
|---|---|
| Database (me) | Schema design, migrations, Eloquent models, data dictionary |
| Backend | API endpoints, business logic, authentication |
| Frontend | UI, forms, report rendering |
| QA | Test cases, validation flows |
| AI | Damage classification module |

Coordinating between tracks required maintaining a living ERD and a versioned data dictionary shared with all teams. Schema changes went through a review process before migration to avoid breaking downstream dependencies.

---

## Challenges and decisions

The most significant challenge was a **schema scope conflict** early in the project: the backend team had begun building against a 4-table prototype, while the actual requirements demanded 54. Resolving this required a full schema review session, a migration reset, and clear documentation of the canonical model going forward.

Designing for **forensic accuracy** also meant resisting the temptation to simplify. Fields that seemed redundant (e.g., multiple timestamps, duplicate measurement columns) often existed for legal traceability reasons.
